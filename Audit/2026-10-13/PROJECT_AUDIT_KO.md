# 안성제철 구현 현황과 개선 우선순위

2026년 10월 13일, `develop`의 `42e05e4` 기준. 점검 시작 당시 Git 작업 트리는 깨끗했다.

**현재 단계는 펀치 중심의 협동 전투를 시험할 수 있는 통합 프로토타입이다. 전투 판정과 LAN 권한 처리는 상당 부분 구현돼 있지만, 관람객이 VR 안에서 처음부터 끝까지 체험하는 게임으로는 연결과 완성도가 부족하다. 특히 플레이어 로봇 팔 모델 참조, 조종사 아바타 동작 연결, VR 접속 UI를 먼저 해결해야 한다.**

완성도를 단일 백분율로 표현하지 않았다. 이미 만든 보스 공격 14종을 실제 통합 전투에서도 사용할 수 있는 것으로 세면 진행률이 크게 부풀려지기 때문이다. 기획의 미정·보류 항목도 확정 구현 누락과 구분했다.

## 조사 범위와 검증 결과

- Git 추적 파일 6,864개, 약 931 MiB의 파일 목록·종류·용량을 조사했다. `.git` 이력 용량, Unity `Library`, 로컬 빌드·검증 결과는 이 용량에 포함하지 않는다.
- `_Project`, `_BossPrototype`, `CockpitVariants`의 자체 C# 파일은 124개, 총 13,076줄이다. 핵심 런타임 코드, 빌더, 검증 진입점, 씬·프리팹 연결과 설정을 조사했다. 모든 텍스처 픽셀이나 Blender 내부 객체를 수동으로 전수 검사한 것은 아니다.
- 메인 프로젝트의 추적된 Unity 씬 26개를 목록화하고 스크립트 참조를 조사했다. `SampleScene`, `BossModelTest`, `sunwoo_IntegratedPlay`는 Unity에서 직접 열어 확장된 프리팹 구조까지 검사했다.
- Unity 6000.3.24f1에서 새로 컴파일하고 기존 순수 전투 검사 27개, 통합 규칙 검사 27개가 통과했다.
- 현재 통합 씬의 Play Mode에서 준비 중 공격과 정지 상태 회피 문제를 재현했다. 현재 렌더도 새로 저장했다.
- 기존 통합 Play Mode·LAN·HUD 검증 기록도 읽었다. 이번에 전체 LAN 다중 프로세스 검사를 다시 실행하거나 Android 빌드를 만든 것은 아니다. 실제 HMD, 두 PC, 외골격, 체감 성능은 이번 검증 범위에 포함되지 않는다.
- 정적 GUID 조사에서 126개의 해석되지 않은 파일/GUID 조합이 나왔다. 샘플·선택적 패키지·비활성 잔여 참조가 섞이므로 이 숫자를 게임 버그 126개로 해석하면 안 된다. 아래에서는 실제 Unity 경고와 실행 결과로 확인한 모델 참조를 별도로 다룬다. 활성 자산 경로의 중복 GUID는 발견하지 않았다.

근거 파일: `inventory.json`, `unity-audit-02-results.txt`, `unity-visual-results.txt`, `combat-checks.txt`, `integrated-rules-checks.txt`, `current-integrated-view.png`. 모두 이 보고서와 같은 디렉터리에 있다. 첫 점검 스크립트의 Unity null 처리 오류는 보정 후 재실행했으며, 최종 근거는 `unity-audit-02`와 `unity-visual` 실행이다.

| 드론 구간·요격 | 미구현 | 보스의 미사일 실험 코드는 플레이어 드론 페이즈와 다름 |
| 협동 필살기 | 미구현 | 지속 가슴 광선 입력/진행 없음. 보스 레이저와 구분 |
| 외골격 모터 | 저장소 게임에 미연결 | 피드백 확장 인터페이스는 있으나 시리얼/모터 어댑터 없음 |

검의 역할, 좌우 무기 분담, 일부 버튼 배치와 수치는 문서에서도 미정·보류 또는 회의안이다. 이 항목들은 구현 전에 최신 확정안을 정리해야 한다. 다만 현재 해당 플레이어 무기 시스템이 없다는 코드상 사실은 분명하다.

## 먼저 고쳐야 할 확인된 문제

### 1. 플레이어 로봇 팔의 모델 참조가 끊겨 있다

**우선순위 높음.** `sunwoo_IntegratedPlay.unity:22438`의 `Uploaded rig - playable arms`가 GUID `6bac2a1fb3671154babb96bd29e3fad7`의 FBX 프리팹을 참조하지만, 이 GUID를 가진 자산 메타가 없다. 같은 GUID의 오래된 표적 인스턴스도 남아 있다(`:5721`). Unity에서 Missing Prefab 경고 2개가 실제 발생했다.

`RobotPlayBuilder.cs:16`이 사용하는 v025 파일은 현재 `mecha-red-points-mixamo-v025.fbx`이며 메타 GUID는 `de68ce75bca22c1408fad65dbfd0ff3a`다. 별도 오래된 렌더러들은 존재하지 않는 `fd67f3d30312eb246a738331dc7b5cbd` 메시/재질도 참조한다. 파일이 디스크에 있다는 사실만으로 기존 씬 참조가 복구되지는 않는다.

실행 후 활성 렌더러 목록에는 `Shared Robot Body`가 없었다. 로봇 전투 판정은 살아 있어 보스 HP가 줄지만, 팔 모델 표시가 따라오지 않는 상태다. 조종석의 사람 손 모델과 별도 문제다. 모델 GUID·내부 fileID·본 바인딩을 확인해 팔 프리팹을 복구하고, 실제 좌우 팔이 보이는지 검증해야 한다. 문자열 GUID만 무조건 치환하면 내부 메시/본 fileID가 달라 다시 깨질 수 있다.

### 2. 기본 빌드가 자체 게임으로 시작하지 않는다

**우선순위 높음.** `ProjectSettings/EditorBuildSettings.asset:9`의 첫 활성 씬은 `Assets/Scenes/SampleScene.unity`다. 이는 VR Multiplayer 예제 환경이다. 통합 게임은 세 번째 활성 씬이고, 샘플에서 통합 게임으로 넘어가는 게임 진입 경로는 확인되지 않았다.

반면 `IntegratedNetworkBuild.cs:12`는 통합 씬만 넣어 별도 Windows 검사용 실행 파일을 만든다. 즉 “검사 빌드는 실행된다”와 “일반 Build And Run이 게임을 실행한다”가 다르다. 발표/배포용 진입 씬과 프로필을 명시해야 한다.

### 3. 통합 씬에서 조종사 팔이 실제 입력을 따라가지 않는다

**핵심 경험 문제.** 통합 씬의 `ArmMotionInput`은 비활성이고, 원래 아바타의 `Follow`를 호출하던 코드는 `ArmMotionInput.cs:240`에 있다. 대신 켜진 `RobotPilotInput`은 전투 세션과 카메라를 갱신하지만 `CockpitPilotAvatar.Follow`를 호출하지 않는다.

`CockpitPilotAvatar.LateUpdate`는 현재 타깃을 평가할 뿐, 컨트롤러 입력을 새로 공급하지 않는다. 로컬 머리 정렬 일부는 유지되지만 팔 타깃은 준비 자세에 남는다. 온라인 스냅샷에도 파일럿 머리·양손 회전/보조 손 정보가 없다. “옆 동료와 함께 거대한 로봇을 조종한다”는 기획의 중요한 감각이 빠져 있다.

해결은 로봇 판정용 입력과 파일럿 표시용 입력을 명시적으로 연결하고, 상대 파일럿의 표시 자세를 별도로 복제하는 것이다. 과거 입력 컴포넌트를 그냥 다시 켜면 카메라와 키 바인딩 소유권이 충돌할 수 있다.

### 4. VR 안에서 접속과 시작을 완료하는 UI가 없다

`IntegratedOnlineState.cs:111` 이후의 HOST/JOIN/IP/START는 화면 좌표 기반 `OnGUI`다. `IntegratedCockpitSelector.cs:33`도 동일하다. 설정 화면은 `SuitHudController.Update`의 ESC로 열린다.

현재 통합 Play Mode에서 생성된 레이캐스터는 `GraphicRaycaster` 하나였다. 별도의 XR UI 입력/포인터 연결을 확인하지 못했다. 샘플 씬에는 `XRUIInputModule`, `TrackedDeviceGraphicRaycaster`가 있지만 통합 씬으로 이전되지 않았다. 운영자가 PC에서 조작하는 시연은 가능해도 HMD와 컨트롤러만으로 입장→준비→시작→설정을 완결할 수 있는 구성은 아니다.

### 5. 준비 중에도 보스를 공격할 수 있다

**재현됨.** 오른팔 입력을 보내지 않아 `Calibrating`을 유지한 상태에서 왼팔만 중립→잽을 반복했다. 3회 명중으로 보스 HP가 160에서 136으로 줄었다. 캡처에도 READY 안내와 감소한 보스 HP가 함께 나온다.

`RobotPlaySession.TryPunchContact`(`:329`)는 온라인일 때만 Battle 여부를 확인한다. 오프라인에서는 `trainingWindow`가 열려 있어 준비 중 타격을 허용한다. 학습 단계 역시 Battle에서만 진행하므로 준비 중 피해와 학습 진척이 어긋난다. 공격·부스트·이동·피해의 허용 상태를 오프라인/온라인 공통으로 정해야 한다.

### 6. 가드 불가 공격이 정지 위치만으로 회피된다

**재현됨.** 로봇 X좌표를 0.6으로 둔 채 이동 입력 0, 실제 로봇 몸 콜라이더가 타격 후보에 들어오는 조건으로 Impact를 호출했다. 피해 0, DodgeCount 1이 됐다.

`IntegratedBossEncounter.cs:54`은 `Abs(robotRoot.position.x) >= sidestepDistance`만 확인한다. 이번 공격에 맞춰 협동 이동했는지, 공격 시작 위치에서 얼마나 이동했는지는 검사하지 않는다. 한 번 옆으로 이동한 후 머물러도 반복 가드 불가 공격에서 이 조건을 만족한다. 공격별 기준 위치와 회피 유효 시간을 기록하거나, 실제 회피한 충돌 관계로 판정해야 한다.

### 7. 보스 공격 자산은 많지만 실제 플레이의 다양성은 적다

`IntegratedBossEncounter.cs:46`은 공격 종류를 3개로 순환하고, 모두 `driver.TryPunch()`를 호출한다. 일반/강공격/가드 불가의 차이는 경고 문구와 피해·가드 규칙이다. 시각적으로는 같은 오른손 펀치다.

보스 프리팹에 `BossCombatController`가 붙어 있어도 통합 진행이 `TryAttack`을 호출하는 것은 아니다. 실험실의 검·미사일·잡기·레이저를 통합 게임 기능으로 세면 안 된다. 또한 시험 수신기 `BossCombatTarget`은 일반 가드 시 기본 10% 피해와 패링을 지원하지만, 플레이어 `RobotCombat`은 성공 가드 0피해다. 연결 전에 체력/가드/상태이상 규칙을 하나로 맞춰야 한다.

### 8. 온라인에서 손 회전 정보가 사라진다

`RobotPlaySession.SetLocalHandRotation`(`:346`)은 오프라인에서만 회전을 저장한다. `Pose`(`:365`)는 네트워크 활성 상태에서 `Quaternion.identity`를 강제로 사용한다. RPC와 스냅샷에도 손 회전이 없다.

이로 인해 오프라인에서 확인한 컨트롤러 회전에 따른 팔꿈치/전완 표현과 온라인 표현이 같지 않다. 손목을 단단히 고정하는 설계 자체와, 필요한 회전 데이터를 전혀 전송하지 않는 문제를 구분해야 한다.

## 플레이 품질과 기획 차이

1. **이동은 전장 탐색이 아니라 작은 시험 구역 이동이다.** `RobotPlaySession.cs:282`는 X를 -0.7~0.7, Z를 -1~0.15로 고정한다. 공격 거리로 자동 접근·후퇴·정지하는 동작, 회피 재사용 조건, 보스 자동 대면은 없다. 좌표 클램프는 맵과 기체 위치를 바꾸면 곧바로 문제가 되는 구현이다.
2. **보조 손 스틱이라는 기획과 입력 경로가 다르다.** 협동 이동이 켜지면 `RobotPilotInput.ReadXR`은 왼쪽 조종사의 왼 스틱, 오른쪽 조종사의 오른 스틱을 읽는다. 문서의 “반대 손으로 이동·보조 기능”과 대조해 최종 버튼 배치를 확정해야 한다.
3. **가드는 높이 중심 판정이다.** `RobotCombat.Sample`은 손 높이와 궤적 상태로 guarding을 정한다. 몸 앞의 위치·방향·보스 타격 방향과의 관계는 충분히 사용하지 않는다. 현재는 실기기에서 배우기 쉬운지, 옆/뒤로 든 손도 가드가 되는지 튜닝해야 한다.
4. **연계 협동 안내가 부족하다.** `NextSide`는 상태에 있지만 통합 HUD는 `COMBO n/2` 위주로 표시한다. 다음 담당 팔, 남은 시간, 실패 이유, 중립 복귀 필요가 눈에 잘 들어오는 안내로 연결되지 않는다.
5. **튜토리얼 경로가 실제 다음 행동을 반영하지 않는다.** `IntegratedCombatHud.LateUpdate`는 늘 왼팔 중립점에서 보스 중심으로 향하는 3점 경로를 공급한다. 오른팔 차례나 훅 궤적에 맞춰 바뀌지 않는다. 손 따라하기 안내가 실제 판정과 어긋날 수 있다.
6. **5분은 표시 값이다.** `IntegratedPlayFlow.targetDurationSeconds=300`은 HUD 문자열에 사용한다. 보스 HP 160, 잽 8, 훅 20, 부스트 포함 콤보 56의 시험값으로만 진행된다. 튜토리얼을 충분히 배우기 전 빨리 끝나는 경우와 초보자가 오래 멈추는 경우를 제어할 체험 구성이 필요하다.
7. **시작과 종료 연출이 비어 있다.** 기체 연결 확인, 정비고/출격, 단계 전환, 최종 광선, 결과 요약은 현재 준비/승패 텍스트로 대체된다.
8. **부위 손상은 실제 해부학적 타격이 아니다.** 통합 보스 표적은 BoxCollider 하나이고, 보스 모델 하위 콜라이더는 빌더에서 꺼진다. 받은 피해는 일반/가드 불가→오른팔, 강공격→몸통으로 매핑한다. 왼팔·머리·다리 상태 그림이 있어도 해당 부위의 실제 피해 시스템이 완성된 것은 아니다.
9. **부스트의 후퇴는 보이는 동안만 적용된다.** `IntegratedPunchCue`가 카메라 렌더 시작/끝에 모델 위치를 밀었다가 복원한다. 전투 거리와 충돌 상태는 그대로다. 기획의 날려버리기를 실제 후속 전투 변화로 쓰려면 권한 상태와 애니메이션을 함께 설계해야 한다.
10. **장비 체험 요소가 아직 소프트웨어 모의 수준이다.** 컨트롤러 진동은 구현됐지만 외골격 모터 어댑터는 없다. 문서에 있는 다른 팀원의 하드웨어 검증을 이 프로젝트에 연결된 기능으로 간주하면 안 된다.

## 화면과 아트 평가

이번 점검에서 캡처한 `current-integrated-view.png` 기준으로 콕핏 프레임, 파일럿 손, 투명한 청록 HUD와 보스의 기본 재질은 확인된다. 보스와 마주 보는 구조는 분명하다.

다만 기본 시점에서 상부 프레임이 보스 머리와 상체 일부를 가리고, 하단 전투 텍스트는 손/콘솔 근처에 작게 배치된다. 배경은 검은색과 단순 바닥 위주라 거대 기체의 규모와 장소를 설명할 시각적 기준이 부족하다. HUD는 조형적 요소에 비해 다음 행동을 알려주는 정보의 크기와 우선순위가 약하다. 이것은 이번 데스크톱 카메라 렌더에 대한 평가이며 실제 HMD 가독성과 양안 시야는 별도 확인이 필요하다.

ArtSource의 최신 BossV11과 현재 Unity 보스는 다른 단계의 자산이다. 새 보스의 디자인 검증, Unity용 메시/재질 정리, 리깅·애니메이션 호환, 충돌체, 크기/거리, 성능까지 적용해야 교체 완료다. 원본 Blender 파일과 리뷰 렌더만 존재하는 상태에서 이 과정을 완료로 세면 안 된다.

소리는 버튼 클릭, HoverSound, NegativeSound, CoinSplash가 임시 타격·가드·피격·부스트에 연결돼 있다. 기계 구동, 금속 충돌, 경고, 보스 예고, 출격, 환경음, 음성 안내가 게임 리듬을 만드는 단계는 아직 부족하다.

최종 실행 환경은 아직 미정이며, 사용자 확인에 따라 **PC VR과 Quest 3 단독 실행을 모두 후보로 평가한다.** 실제 FPS나 GPU 시간을 측정한 결과는 아니다. 아래는 코드·씬에서 확인된 비용 구조이며, 한 환경에서의 검사 결과를 다른 환경의 실행 가능성으로 확대하지 않는다.

| 보스 스킨 | 독립 보스 씬에서 SkinnedMeshRenderer 291개 | 작은 스킨이 다수. 애니메이션·바운드·컬링·드로우 비용을 함께 확인 |

| 보스 손 위치 검색 | `HandPoint`에서 매번 계층 전체 검색과 LINQ | 공격 실험실을 통합하기 전에 본 참조 캐시 필요 |

Android는 ARM64와 IL2CPP 설정, OpenXR/Quest 기능이 있다. 이것만으로 Quest 단독 성능과 배포 가능성을 보장하지 않는다. 현재 전용 검사 빌더는 Windows용이고 `applicationIdentifier`는 `com.DefaultCompany.VRMultiplayer`다. PC VR도 현재 3중 전장 렌더와 많은 스킨을 그대로 두고 성능을 낙관할 근거는 없다.

### 실행 환경을 결정하기 위한 비교 기준

| 구분 | PC VR | Quest 3 단독 실행 |
|---|---|---|
| 현재 확보한 근거 | Windows 개발 빌드와 로컬 다중 프로세스 검사 기록 | ARM64·IL2CPP·OpenXR 설정. 실제 Android 실행 근거는 이번 조사에서 확보하지 못함 |
| 먼저 검증할 것 | 실제 PC/HMD 두 조합의 머리·손 추적, 연결 방식에 따른 지연, CPU/GPU 프레임 시간 | Android 빌드·설치·시작, 컨트롤러 입력, 렌더 텍스처·셰이더·메모리·발열과 지속 성능 |
| 네트워크 | 실제 두 PC의 LAN 연결·방화벽·지연·재접속 | 실제 두 Quest의 같은 네트워크 접속·앱 중단/복귀·재접속 |
| 운영 동선 | PC 운영자가 담당할 접속/설정과 HMD 내부 조작의 범위 결정 | HMD 안에서 IP/접속·역할·준비·시작·재시작을 완료하는 동선 필요 |
| 외골격 | 게임 PC와 장치 연결 방식 및 피드백 어댑터 검증 | Quest와 장치 사이 통신 경로를 별도로 설계·검증 |

모델 참조, 아바타 입력, 준비 중 피해, 회피 판정은 두 환경에 공통인 문제이므로 플랫폼 결정 전에도 수정할 수 있다. 이후 동일한 짧은 전투 구간으로 두 환경을 비교하고, 품질 설정을 나누어 전장 RT 해상도·AA·그림자·모델 표현을 조정한다. 목표 화질과 지속 성능, 설치·운영 편의, 외골격 연결 결과를 함께 보고 최종 환경을 결정한다. 현재 자료만으로 어느 한쪽의 완성도나 실기기 성능을 확정하지 않는다.

## 네트워크 평가

잘 구현된 부분은 호스트 권한, 역할 검증, 세 번째 접속자 거절, 명령 순서와 epoch 검증, 재시작 권한, 연결 실패 후 무심코 오프라인 권한으로 넘어가지 않는 처리다. 단순히 위치만 보내는 초기 예제 수준은 넘어섰다.

부족한 부분은 표현 품질과 실제 환경 검증이다.

- 팔 회전과 파일럿 머리/보조 손 자세가 복제되지 않는다.
- `RobotPlaySession.cs:292`는 받은 위치를 직접 적용한다. 표시용 보간이나 예측이 없다.
- 서버는 클라이언트의 원래 샘플 시각이 아니라 입력 도착 시각으로 궤적을 처리한다. 입력이 몰리면 8ms 최소 간격 검사와 속도 검사에서 거절될 수 있다. 실제 지터/손실에서 분류 품질을 확인해야 한다.
- 0.45초 부스트 창처럼 짧은 입력 기회는 왕복 지연에 민감하다. 클라이언트 안내와 서버 마감의 관계를 지연 조건에서 검사해야 한다.
- 접속은 IPv4 수동 입력이다. 템플릿에 세션/음성 코드가 있어도 통합 LAN에서 자동 검색, 같은 방 목록, 음성 채팅까지 제공되는 것은 아니다.
- 기존 `OnlineProcesses-20261013-014054/online-checks.txt`는 PASS로 종료하며 마지막 줄에 HMD/두 실제 PC 미검증이 명시돼 있다. 이번 점검은 해당 기록을 확인했으며 이 기록을 새 실행 결과로 주장하지 않는다.

## 코드 구조와 유지보수

1. `RobotCombat`을 Unity 씬과 분리한 순수 상태 머신으로 둔 점은 좋다. 이것이 기존 규칙 검사를 빠르게 수행할 수 있게 한다.
2. 반면 전투 권한·전송·입력 수신·물리 포즈·HUD 진단이 `RobotPlaySession`에 모여 있다. 연결 계층, 권한 시뮬레이션, 표시 계층을 분리하면 수정 영향이 줄어든다.
3. `ArmMotionInput`, `RobotPilotInput`, `MechaVRHandTarget`에 서로 다른 입력/보정 경로가 있다. 실험 기능이 통합 경로로 옮겨지지 않는 원인이 된다.
4. `RobotCombat`, `BossCombatController`, `BossCombatTarget`, HUD 손상 상태가 별도 체력을 가진다. 보스 공격을 연결할 때 피해를 이중 적용하거나 서로 다른 체력을 표시하지 않도록 소유권이 필요하다.
5. 자체 스크립트 중 29개는 한 줄 길이가 300자를 넘는다. 압축된 여러 문장, 중첩 삼항식, 긴 단일 줄 메서드가 리뷰·디버깅·병합을 어렵게 한다. 핵심 전투/LAN 경로부터 일반적인 형식으로 정리하는 편이 좋다.
6. 오브젝트 이름, 레이어 숫자 27/29/30/31, 파일 경로, 월드 좌표를 직접 의존하는 부분이 많다. 씬 변경 시 조용히 기능이 빠질 수 있다. 필요한 참조와 검증을 에디터에서 명시하는 것이 좋다.
7. 현재 게임 조정값은 여러 MonoBehaviour와 직렬화된 클래스에 흩어져 있다. 기획에서 확정한 규칙과 실험 수치를 한 튜닝 자산/설정으로 추적할 필요가 있다.
8. 기존 리그와 장면 생성 도구는 제작 속도에 유용하지만, 무조건 다시 생성하는 방식은 수동 작업과 충돌한다. 생성 범위와 수동 편집 범위를 명확하게 해야 한다.
9. README의 예전 “접촉 전 부스트”와 최신 “명중 후 부스트” 설명이 공존한다. 프로토타입별 차이일 수 있으나, 현재 통합 게임 사용법이 먼저 보이도록 정리해야 한다.
10. `VR_test`의 복사된 접촉 코드는 현재 메인과 별도 프로젝트다. 공통 부분을 수정할 때 어느 쪽을 기준으로 유지할지 정해야 한다.

## 검증 체계에서 빠진 부분

현재 테스트는 강점이지만 통과 개수만으로 완성도를 판단하면 안 된다. 이번에 순수 규칙 54개가 통과했어도 준비 단계 피해와 정지 회피, 모델 참조 문제는 남았다.

- **현재 저장된 씬 그대로의 부팅 검사:** `IntegratedPlayValidation.Run`과 `IntegratedNetworkBuild.Build`는 먼저 `UpdateOwnedScene`을 호출해 씬을 수정·저장한다. 점검하려는 원래 씬을 정상 상태로 보정한 뒤 테스트할 가능성이 있으므로, 변경 없는 검증과 재생성 검증을 분리해야 한다.
- **시각 모델의 존재 검사:** 콜라이더와 HP만 정상이어도 플레이어 팔 메시가 사라질 수 있다. 좌우 모델·메시·재질·본·활성 렌더러를 검사해야 한다.
- **실제 시작 경로 검사:** 일반 빌드 첫 씬에서 VR 컨트롤러만으로 입장→전투→승패→다음 체험까지 이어지는지 확인해야 한다.
- **게임 상태 경계 검사:** 준비 전, 한 손만 준비, 연결 대기, 재보정, 종료 직후, 메뉴 열린 상태의 입력과 피해 규칙을 명시해야 한다.
- **회피 검사:** 공격 전부터 옆에 서 있던 경우, 반대 방향 입력, 제자리 유지, 늦은 이동, 실제 충돌 후보가 있는 경우를 포함해야 한다.
- **실사용자 검사:** 초보자 좌/우 잽·훅·가드의 오인식/미인식, 키·팔 길이·앉기/서기 차이, 손 추적 상실 복구, 실제 햅틱/음향을 기록해야 한다.
- **실제 네트워크 조건:** 서로 다른 PC/HMD, 지연·지터·손실·끊김·복구 상태에서 같은 동작을 검증해야 한다.
- **성능:** HMD별 CPU/GPU 프레임 시간, 최악 충돌 프레임, 메모리와 장시간 실행 안정성을 확보해야 한다.
- **결과 추적:** 검증 결과에 소스 커밋, 빌드 식별자, 씬, 플랫폼, 설정을 남겨 오래된 실행 파일의 PASS와 현재 소스를 연결해야 한다.

## 권장 작업 순서

### 첫 번째 완료 기준은 현재 펀치 체험을 안정적으로 보여주는 것

1. 플레이어 팔 모델과 오래된 GUID 참조 복구. 새로 열어도 Missing Prefab이 없고 좌우 팔이 실제로 표시되는지 확인.
2. 통합 게임을 시작하는 정식 빌드 프로필 마련. 기본 실행에서 샘플 로비로 들어가지 않도록 정리.
3. 조종사 아바타 팔과 머리, 상대 표시 연결. 로봇 팔과 사람 팔이 같은 동작을 일관되게 보여주도록 검증.
4. 오프라인/온라인 공통 진행 상태로 준비 중 공격을 막고, 회피를 공격별 시점과 이동으로 판정.
5. VR 접속·준비·시작·재시작·설정 UI 연결. PC 운영자가 필요한 항목도 의도적으로 정리.

### 두 번째 완료 기준은 2인이 이해하고 즐길 수 있는 보스전

6. 일반·강공격·가드 불가의 모션/소리/색/예고를 구분. 기존 보스 공격에서 실제로 채택할 소수를 먼저 연결.
7. 다음 콤보 담당자, 남은 시간, 중립 복귀, 실패 이유를 HUD·소리·진동으로 명확히 안내.
8. 접근·후퇴·회피 거리, 보스 거리·시야, 가드와 펀치 임계값을 실제 두 사람이 테스트해 결정.
9. 전용 타격/가드/피격/부스트 음향과 기체 구동·경고를 연결.
10. 튜토리얼 완료 조건과 난이도·HP를 조정해 목표 체험 길이와 성공 경험을 설계.

### 세 번째 완료 기준은 발표/전시 환경에서 반복 운영되는 것

11. 렌더러/재질 통합, RT 해상도와 AA, 충돌 반복 비용을 프로파일링하고 목표 기기에서 조정.
12. 실제 두 PC/HMD에서 연결·재접속·역할·자세·햅틱·오디오를 검증.
13. 배경·출격·승패·다음 사용자 초기화를 연결하고 사용법 문서를 현재 버전으로 통일.
14. 그 다음 확정된 무기, 드론, 필살기, 외골격 통신을 단계별로 확장.

검·총·미사일을 한꺼번에 추가하기 전에 첫 번째 완료 기준을 통과시키는 것이 효과적이다. 이미 있는 전투 규칙과 보스 자산을 살리면서, 실제 보이는 몸과 입력·진행·UI가 한 게임으로 이어지도록 만드는 작업이 가장 크게 체감된다.
